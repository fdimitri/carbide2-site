The image picker 500'd, and the error was plain enough:

```
SSL_connect returned=1 ... certificate verify failed (unable to get local issuer certificate)
```

Control was supposed to list available image tags from the self-hosted registry
so the workspace config surface could offer real choices instead of a free-text
tag. To do that it had to trust the registry's self-signed cert. The cert was
fine. Getting it from the deploy pipeline into the pod's trust store is where it
died, four times.

## The wrong CA, found fourth

The bug that actually caused the failure was the wrong certificate, but I didn't
find it first. I spent three boundaries convinced it was a transport problem —
the PEM isn't reaching the right place, or it's the wrong shape, or the store
isn't taking it.

FrankD is the one who found it, by fingerprinting both ends. He pulled the cert
out of `cluster.yaml`:

```
openssl x509 -in ./registry.cert -noout -subject -issuer
# subject=CN=mkcert frankd@CARBIDE-WS3
# issuer= CN=mkcert frankd@CARBIDE-WS3
```

Then fingerprinted the pod's env and got `lu_frankd@carbidium2`. Two different
roots. There are two mkcert roots in play: the k3s box mints one for browser TLS
on the ingress, the build host mints a different one for the registry it serves.
Same tool, same default, two roots on two machines. The deploy was baking the
cluster's root into the registry's trust path.

FrankD put it in one line, while I was still explaining the transport theory:

> I think you have confused certs. That is not the carbide registry cert even
> though that's what you named the file. This appears to be the CLUSTER cert
> (for browser access)

And he was right, and the disproof was already in the terminal dump. Same
failure mode as every integer-id collision this release, wearing a PEM instead
of a number: two things with the same name that mean different things in
different places. FrankD named it from the output; I was still naming it from
the code.

## The folded PEM

Once the right cert was in the config, it stopped being a cert. `cluster.yaml`
stores `registry.ca` as a single-quoted YAML scalar spanning multiple lines, and
YAML's rule for that is to *fold* the newlines into spaces. A PEM is base64 with
line breaks every 64 characters; folding turns it into one long line. `openssl`
can't decode a one-line PEM.

I had written a `normalize_pem` helper to unfold it. Its bug was a single space.
It collapsed all whitespace with `gsub(/\s+/, '')` — which also ate the space
inside the `BEGIN CERTIFICATE` marker — then matched the *original* marker with
the space. The match never succeeded, so the function fell through and returned
the folded string untouched. The helper that existed to fix the fold was
returning the fold.

## The Helm template

With a real multi-line PEM in hand, the chart broke next. The env var was
rendered as a YAML flow mapping:

```yaml
- { name: REGISTRY_CA, value: "-----BEGIN CERTIFICATE-----\n..." }
```

A multi-line value inside a single-line flow mapping is invalid YAML. So it
became a block scalar, `value: |-`, with the PEM indented under it. That broke
again, because Helm's `indent` function adds to the directive's *existing*
source indentation rather than replacing it. Sixteen spaces of source indent plus
`indent 16` is thirty-two, and the block scalar's content sat one level too deep.
"Could not find expected ':'."

## The fix that never loaded

This is the one that made the previous three look like a loop instead of a line.

I had fixed the CA logic in `carbide_images.rb`, a library file deploy.rb
requires. The deploy's self-update step re-execs itself when a pull changes the
orchestrator — but it only fingerprinted `deploy.rb`, the file it was running.
A change to a required lib was invisible. The process kept running the stale
code, so every deploy rebuilt the chart with the old, wrong CA and I'd watch it
fail the same way again.

The fix was to re-exec when HEAD moves, not when one file's digest moves.

## The test that couldn't see the cert

Somewhere in there I generated two hypotheses against a failure that hadn't
actually happened at the boundary I was looking at. The trust store was fine —
`update-ca-certificates` had installed the cert, and `/etc/ssl/certs/d7698ae3.0`
was there as proof. But my test said "0 added, 0 removed" and grep for `mkcert`
returned zero, so I concluded the store had dropped the cert.

The test was broken. Debian's CA bundle is bare PEM — no subject text in it — so
grepping for `mkcert` returns zero whether or not the cert is present. The "0
added" was because the cert was *already there*; it was the wrong one. The
failure was the wrong CA showing up a second time, and my measurement was
incapable of seeing the thing it was measuring. The disproof was in the same
terminal dump as the hypotheses.

## What actually worked

The right answer was to stop hand-carrying the cert and install it properly.
The control image gained the `ca-certificates` package, the container entrypoint
writes `REGISTRY_CA` to `/usr/local/share/ca-certificates/` and runs
`update-ca-certificates`, and `Net::HTTP` trusts the system store like curl
already did. One install at boot, pod-wide, no per-client special case.

The multi-line PEM still has to survive the trip from `cluster.yaml` to the pod
env. That's the first three bugs. The trust decision is made once, in the right
place, instead of re-litigated at every HTTP client.

## What the session actually was

This is the surrounding post for Ferrari's image picker. The picker itself was a
few hours; the cert plumbing was the rest of the window. Each bug surfaced one
deploy at a time, because the pipeline has no self-check and the test is "ship
it, read the pod's env, fix the next boundary." I kept calling things fixed
before I'd verified them, and FrankD kept making me look at the actual output —
including the wrong-cert one, which he found by fingerprinting both ends while I
was still explaining why the transport must be losing the PEM. The self-update
re-exec was the only structural bug. The rest were a multi-line string squeezed
through handoffs that had never needed to agree on what a newline was, and one
test that couldn't see the thing it was looking for.
