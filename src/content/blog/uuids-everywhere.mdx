A workspace came up and couldn't write a file. `fs/tree` returned an empty list,
and `fs/create_file` failed with "Parent directory / does not exist." The
directory existed. The project existed. The request was authenticated. The error
was real but the reason wasn't any of those.

The token said `project_id: 13`. The local project was `id: 1`. Every filesystem
query keyed off the wrong number, so the project looked empty.

## Two databases, one column name

This is the whole saga in one sentence: control has a database, the workspace pod
has a database, and both of them have a `users` table with an integer primary key
called `id`, and both of them have `user_id` columns pointing at it. The token
carries control's `user_id`. The pod stores local `user_id`. Nothing anywhere
says which one a given `user_id` means.

It isn't that one of them is wrong. They're both right, in their own database,
and wrong the moment they cross the boundary. FrankD put it in the sharpest
possible form: workspace UID equals control UID is a fluke, and if they happen
to be the same it's a coincidence, not a guarantee.

I had hit a version of this already and fixed it wrong. When the project-id bug
surfaced, I resolved the token's `project_id` to the local `Project.canonical`
and stuffed that into the session. It worked for the single-project case because
the single project happened to be id 1. It was a correct answer to the wrong
question.

## The fix that wasn't

The user-id version of the same bug came next, and I reached for the same shape
of fix: expose both the local id and the control id, thread the control id into
the record columns. Which is the one thing you must not do, because those columns
are foreign keys to the *local* `users` table.

FrankD asked how I could think that was a fix, why I would use a userid from a
completely separate database. The answer was that I'd stopped thinking of them
as separate. `user_id` looked like one concept and I treated it as one, even
while the whole bug was that it wasn't.

A second pair of eyes caught the concrete failure: a control id written into a
column with a foreign key to local users either raises on insert or silently
points at some other local user who happens to have that number. The
mis-attribution is the worse of the two, because it doesn't error, it just
records that the wrong person did the thing.

## Typed identity

The fix that stuck is to make identity carry its own type across the boundary.
The token's subject and audience became `user:<uuid>` and `workspace:<uuid>`.
The workspace keeps its integer primary keys for its own joins, but anything
that leaves the database travels as a UUID with its kind attached.

FrankD asked why not `type:uuid` everywhere, to be clear — is it a workspace, is
it a user, is it a project, is it an org. That's the right question and it's
why `sub` and `aud` ended up typed rather than bare. A bare UUID still doesn't
tell you which namespace it belongs to; `user:dc10b8bc` does.

There is an "almost" here, because the integers didn't disappear. They're still
the primary keys inside each database, because that's what foreign keys are for
and they're fast. The UUID is the identity for the wire and the mirror, not a
replacement for the local key. Two id spaces remain; they just stop looking
alike at the boundary.

## The rename that never happened

One thing got discussed and not done, and it's worth naming because the UUID
work made it less urgent without making it less true. Both repos have a class
called `User`. The workspace has one, control has one, and they are different
classes in different codebases with different id spaces. A rename to
`WorkspaceUser` and `ControlUser` would have made the conflation impossible to
write by accident, because the name would have carried the boundary.

We talked about it and moved on, and the UUIDs made it a data-level thing that
mostly stops mattering once you stop crossing the boundary with integers. But
the class names are still both `User`, and every LLM or person reading both
repos still has to remember which one they're in. The UUID fixed the wire; it
didn't fix the name.
