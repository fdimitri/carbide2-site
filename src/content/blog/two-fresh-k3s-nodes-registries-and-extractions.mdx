The picker served the wrong client. You would open a workspace on the new box and
get a build with none of the recent UI in it — no picker, no reset specs, an old
router that bounced you back to the dashboard. The build was there. The code that
chose it was certain it had picked the newest, and it had. That was the bug.

## "Newest" was measured on the wrong clock

The client registry keeps every SPA build content-addressed in MinIO and serves
the newest one, where "newest" meant the largest `build_time` — the wall-clock
moment a build was uploaded. That is correct exactly as long as you build in
commit order, and standing up a second machine is when you stop: the tip commit
got built first, then older commits got backfilled. The most recently uploaded
build was sitting on an ancestor of the commit that added the picker, and that is
what got served.

`build-client` now stamps the git committer date into each `manifest.json`,
forced to UTC and formatted Zulu:

```bash
COMMIT_TIME="$(TZ=UTC git -C "$SRC" show -s --date=format-local:%Y-%m-%dT%H:%M:%SZ --format=%cd "$SHA")"
```

UTC Zulu orders lexicographically the same way it orders chronologically, so
nothing in the read path has to parse a timestamp. Both registries do this:

```ruby
.sort_by { |b| [(b.commit_time.presence || b.build_time).to_s, b.sha] }
.reverse
```

`presence` is there so the `||` fires on an empty string, which Ruby treats as
truthy and which would otherwise sort ahead of every real timestamp. `.to_s`
keeps `sort_by` from comparing `nil` against a String, and `sha` breaks ties
between two builds of one commit.

Wall-clock time tells you when a machine did work. It tells you nothing about
which code is ahead. For "which build is newest," the only honest key is the one
git already computed.

## Two tools for the registry

The fix needs a server and control-plane image rebuild to land in-cluster, so it
does not retroactively un-confuse a node that is already running. Cleaning one up
now means deleting the stale builds by hand, which is why `c2r-lsclient` and
`c2r-rmclient` exist: list the client registry as a table, delete builds by
family and SHA, regenerate the index with the same ordering. Both grab a free
local port, forward to MinIO and pull credentials from the cluster secret, and
without `-y` they show you the context and the target list before deleting from
whatever kube-context you happen to be pointed at.

They are the manual stand-in for a retention policy that is deliberately
deferred, since image retention and client-build retention are the same question
and should produce one GC model instead of two that disagree.

## A second node needs a real registry

The reason builds were landing out of order at all is that there is now more than
one place to land them. k3s has a second host — `carbidium2` alongside
`carbidium1` — and multi-node is a different animal from the single k3d box
everything was built on.

The forcing function is images. On one node the kubelet reads images out of the
store you imported them into. A second node has never heard of your image and has
no path to it, so multi-node needs a real registry.

Set `registry.host` and the deploy brings up a `registry:2` container over TLS,
builds immutable per-component SHA tags (`carbide2:<server>-<worker>`,
`carbide2-control:<control>`, `carbide2-shell:<server>`), pushes with
skip-if-exists so a redeploy that changed nothing pushes nothing, and pins the
resulting tags into the control-plane chart via `--set-string` so the operator
consumes them with no operator code change. Each node gets
`/etc/rancher/k3s/registries.yaml` written for it, trusting the registry by FQDN
with the CA inlined.

Leave `registry.host` blank and none of that happens — you get the old k3d/k3s
containerd import path, unchanged. That is the only reason a change this size was
safe to land: single-node development never notices it exists. There is also a
split-host mode, where `--registry.publish-only` builds and pushes from a machine
running no k3s at all and then exits, and `registry.external: true` tells a node
to pull tags someone else already published. The box that builds does not have to
be a box that runs anything.

## What a second node costs you in storage

Binary file bytes live on the workspace PVC, not in Postgres. That is deliberate
and [documented since June](/blog/building-carbide2-architecture) — DBFS holds
text, binaries are tracked as stat and mtime metadata with the content left on
disk. Nothing about that changed.

What changed is the price. With `local-path`, a PVC binds to whichever node the
pod first landed on. On one node that is free. On more than one, a pod that
reschedules elsewhere leaves its binary files behind — text comes back, because
text really is in the database, and anything uploaded does not. A decision that
cost nothing for two months started costing something the day there was somewhere
else to schedule.

So the storage default had to change, and it changed differently per backend:

- **k3s gets Longhorn as the durable default.** Replicated RWO volumes re-attach
  wherever the pod lands.
- **k3d stays on `local-path`.** A single-node throwaway cluster cannot perform
  replication, and Longhorn brings a manager DaemonSet and open-iscsi with it.
- **CNPG stays on `local-path` on both.** It does streaming replication across
  nodes itself. Longhorn underneath it would replicate the replication.

`Carbide::Storage` holds both strategies behind one seam, picked by what the
cluster actually is. Longhorn's default replica count of 3 is worth a glance on
the way past: with two nodes that is one replica that can never be scheduled, so
`storage.longhorn.replicas` has to come down to match the hardware.

## deploy.rb is coming apart into a library

The part I am actually into. `deploy.rb` became an orchestrator over
`scripts/lib/`: `Carbide::Config`, `Command`, `Images`, `Tls`, `Cluster`,
`ControlPlane`, `Node`, `Storage`, with node lifecycle moved out of the deleted
`dev-cluster-*.sh` and `dev-agent-k3s.sh` shell scripts and into Ruby. The script
still runs the same. Underneath it is a set of libraries that a script happens to
call.

That was a direct instruction, and the reasoning came attached: the thing that
brings a cluster up cannot depend on the cluster being up. Node join, registry
trust and certificate minting all run at t=0, before there is an API server or a
service account to authenticate against, so whatever does that work can never be
a container.

The tracking issue had framed the question as a separate repository versus a role
of the control plane. Both options sort the problem by where the code lives, while
the constraint sorts it by when the code runs. Once that is clear the choice
dissolves: the capabilities become a library, a standalone binary that is never
containerized imports it for the pre-cluster path, and an in-cluster surface
imports the same library for anything that needs a cluster to already exist.
Joining a node does not. Scaling a workspace does.

The split cuts more than one way. Once `Carbide::Tls` mints a certificate on its
own and `Carbide::Cluster` joins a node on its own, the caller stops mattering.
`deploy.rb` is one caller. A command that only mints TLS is another. Something
with buttons instead of forty flags is another, and it imports the same modules
rather than being a second implementation that drifts. For now that is an
assertion with exactly one caller behind it.

The same week, **the Decider** finished its substrate: clients out of the pod
image, builds content-addressed in a static tier, a loader that resolves a build
per request, a picker, and now an ordering that tracks git rather than a wall
clock. What it does is serve newest-of-family. What it is *for* is serving
newest-whose-floor-holds. The `floors` field is already in every manifest.
Nothing reads it yet.

## The config is three layers, and the flag names are the paths

`deploy.rb` resolves its configuration from three sources, each merged over the
last, last writer winning:

1. `scripts/defaults.yaml` — every default in the system, in one file. No
   implicit defaults scattered through the Ruby.
2. `--config input.yaml` — a partial override file. Three examples ship:
   `k3d-local`, `k3s-single-local`, `k3s-multinode-longhorn`.
3. CLI flags, which win over both.

I wanted to make this into a subsystem. A schema, validation, a mapping layer
between flag names and config keys, probably a `Config::Schema` class to hold it
all. The instruction that killed all of that was one sentence: make the flag name
*be* the config path.

So `--storage.backend longhorn` and

```yaml
storage:
  backend: longhorn
```

are the same statement written two ways. `--cluster.role join` sets
`cluster.role`. `--registry.host` sets `registry.host`. There is no translation
table because there is nothing to translate — the flag parser writes into the
same tree the YAML parsed into. The piece I was about to build was pure overhead
created by assuming the two naming schemes would be different.

That same reasoning is why the fourth layer never shipped. `deploy.rb` used to be
configured entirely by environment variables — `PUBLIC_HOST`, `HTTP_PORT`,
`RELEASE` and a dozen more you had to `export` before every run or silently get
`localhost` in your certificate CN. The old issue asking to fix that wanted four
layers, keeping env support for CI and backward compatibility.

Env vars were dropped instead, and that was FrankD's call rather than something
the work discovered. An environment layer needs its own schema to map shell-legal
names onto config paths — `CARBIDE_CLUSTER_HTTP_PORT` onto `cluster.http-port` —
and that schema *is* the translation table the flag-name decision deleted. The
tell was in the proposal itself: its YAML sketch used `public_host:` and
`http_port:`, matching neither the environment variables above them nor the
dotted paths that shipped. Three spellings of the same knob, in a document a few
paragraphs long, before anyone had written the code.

One convention worth knowing: `''` means unset or auto-detect, not empty. Leave
`public.host` blank and it falls back to `hostname -f`; leave `cluster.token`
blank and one gets minted.

## Freeze the config, then deploy every node from it

That last part — the token gets minted when blank — is why multi-node bring-up is
a two-step. If every node deployed straight from the template, every node would
mint its own `cluster.token` and you would end up with N single-node clusters that
politely refuse to know each other. So the flow freezes the resolved config once,
and every machine deploys from that frozen file.

```bash
# 1. On the first node: resolve everything, mint the token, write it out, exit.
#    --yaml-out writes and stops. It does not deploy.
./scripts/deploy.rb --config examples/k3s-multinode-longhorn.yaml \
    --cluster.server-url https://<this-node>:6443 --yaml-out cluster.yaml

# 2. Deploy the first node from the frozen file. The token is present now,
#    so it's reused rather than re-minted.
./scripts/deploy.rb --config cluster.yaml

# 3. On every other node, the same file and one extra flag.
./scripts/deploy.rb --config cluster.yaml --cluster.role join
```

What comes out of step 1 is a fully resolved cluster description — nothing left
to inherit, nothing auto-detected on a machine that might detect it differently:

```yaml
cluster:
  backend: k3s
  name: carbide-dev
  role: init
  server-url: 'https://carbidium2.carbide.local:6443/'
  token: (32 hex bytes)
registry:
  host: carbide-registry.carbide.local
  port: '5000'
  ca: '-----BEGIN CERTIFICATE-----
  …
  -----END CERTIFICATE-----'
  external: true
storage:
  backend: longhorn
  longhorn:
    version: 1.7.2
    replicas: '2'
# … plus the orchestration toggles, control plane, public URL and TLS options
```

Note `registry.ca`. The CA is inlined as PEM text, so the config is the only
artifact that has to reach the other machines — there is nothing to `scp`
alongside it and keep in sync. Copy one text file, run one command.

Which makes a small review finding not so small.
`Carbide::Config#emit_and_exit!` writes that file with a plain `File.write`, so
on a typical umask it lands 0644. This is the one file in the system *designed*
to hold a live join secret and *designed* to be copied between machines, and it
was world-readable on every host it touched.

## What isn't done

Two nodes join, schedule and pull. Storage is decided and wired. The deployer has
a clear pre-cluster line down the middle of it. That is the good news.

Node *remove* does not exist. Adding one is scripted; taking one out — drain,
cordon, delete, without wedging anything — is not, and it belongs to the
deployer-shape decision rather than the bring-up test that just closed.

And the commit-time ordering is only live where the image has been rebuilt, so a
node still running the old server and control images will keep handing out an
ancestor until it rolls. The tools above will prune a confused node in the
meantime.
